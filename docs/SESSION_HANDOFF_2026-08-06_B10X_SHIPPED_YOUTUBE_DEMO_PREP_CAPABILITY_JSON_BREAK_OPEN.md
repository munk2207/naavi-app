**Demo 1 compound-turn date bug — root-caused twice, fixed for real on the second pass.**

- First finding (build 314→315): Claude's own confirmation TEXT sometimes paired the correct weekday name with the wrong day-of-month ("Monday, August 11" when the real event was Monday, August 10), even though the underlying tool-call data was correct. Fixed by recomputing the weekday+date phrase deterministically from the resolved action data instead of trusting Claude's freehand arithmetic (`hooks/useOrchestrator.ts`).
- Wael re-tested on build 315 and the SAME wrong text still showed on the **first** proposal bubble (before saying "yes"). Root cause #2: the correction only ran when `dedupedActions.length > 0`, but the proposal turn never has actions yet — those only exist after confirmation. So the fix could never reach the exact turn the user actually reads. Fixed by adding a fallback (`correctWeekdayDatePhraseFromToday`) that recomputes the date from today using the weekday NAME Claude already gets right (confirmed via live evidence — the weekday name was correct both times, only the day-of-month was wrong), and dropping the `dedupedActions.length > 0` guard so the correction runs on the proposal turn too. Shipped as build 316, confirmed correct live.

## What's still open — capability-answer JSON format break

**Symptom:** "Tell me about your four top capabilities" produces a response that breaks out of the required `{"speech":..., "display":...}` JSON format entirely — Claude writes plain text ending in a literal `---` separator followed by `display:` as a visible field label, which the mobile client correctly renders as raw fallback text (there's no valid JSON to parse, so `parseResponse`'s "no JSON in response" branch shows everything verbatim — this part of the client is behaving exactly as designed, the bug is upstream in what Claude generates).

**First fix attempt (deployed, NOT yet confirmed working):** the capability-length rule hardcoded "2-3 capabilities," directly conflicting with the user asking for a specific count of four. Rewrote the rule so the capability count follows what's actually asked (shrinking each point to stay in the 150-200 word budget instead of exceeding it), and added an explicit, unconditional line reinforcing that the response must always be valid JSON regardless of requested count — never plain-text field labels or separators. Deployed to `get-naavi-prompt` on staging, verified via direct `curl` that the new rule text is being served, committed (`709aa8c`), pushed.

**Wael retested immediately after and got "exactly the same" broken output.**

**Leading theory, NOT yet confirmed:** `naavi-chat/index.ts` has its own separate in-memory prompt cache (`promptCache`, 5-minute TTL, module-level `Map`, keyed by `channel:clientTimezone` — see `naavi-chat/index.ts` around line 1341). This means `naavi-chat`'s warm Edge Function instance could still be serving the prompt text it fetched and cached BEFORE the `get-naavi-prompt` redeploy, independent of the source being updated. The natural next step — redeploying `naavi-chat` itself (no code change needed, just to force its warm instance to restart and re-fetch a fresh prompt) — was queued but the tool call was rejected by Wael before it ran, and the session was closed to hand off instead.

**This is a theory, not a confirmed diagnosis.** It's entirely possible the retest also happened within the 5-minute cache window and this is exactly it, or it's possible something else is still wrong with the rule itself and the cache isn't the (only) issue. Whoever picks this up should not skip verification — confirm the cache theory directly (e.g., check `naavi-chat`'s own logs for prompt-fetch timestamps, or just redeploy `naavi-chat` and retest cleanly) before assuming it's solved.
