**THE RULE. To add a sixth item, one must first be moved out. No exceptions, no "temporarily six."**

**Items MOVE here — they are never copied.** A row lives either in this table or in the general list
below, never both. That is what killed the old queue: it described every item a second time, and the
two copies drifted. **Position in this table is the priority. Top is next.** No P0/P1 labels, no tier
numbers, nothing to keep in sync.

**Why the cap exists, in Wael's words:** *"If you want to put a new one, WE MUST deprioritise another.
This will force us in cleaning and closing items."* Every other mechanism in this document recorded
state and hoped someone would act. **A hard cap makes the cost of adding immediate**: you cannot take
on a sixth thing without deciding what stops being important.

**It is enforced, not remembered.** `node scripts/priority-cap-check.js` counts the rows below and
refuses a push at six (`.githooks/pre-push`). This document has watched a queue, an architecture
reference and a parity audit all decay because nothing forced them to stay true. **Make it refuse,
do not make it warn.**

**Moving OUT is not closing.** Deprioritised items go back to the general list intact. Closed ones go
to `Closed items`. Nothing is ever deleted (Wael, 2026-08-22).

**⭐ What "never deleted" covers — and what it does not (Wael, 2026-08-25).** *"The rule is for
elements that already started or have work. It is not for items that were suggested and denied."*

- **Never deleted:** anything real — an item that was worked on, investigated, deprioritised, or
  closed. Its reasoning is history and history is kept, in `Closed items` or the archive.
- **Deleted outright:** a row that should not have existed. A suggestion that was rejected, or an
  entry created without the approval Rule 1b requires. **Closing it would be worse than deleting
  it** — filing a denied suggestion under `Closed items` records it as legitimate work that got
  finished, which is a false history and makes the closed archive less trustworthy over time.

## Classification scheme

Four lists (Bugs, Features, Tooling, Ideas). **Column shape corrected 2026-07-17** — the original description ("same column shape" for everything) never matched actual practice:
- **Open tables** (Bugs/Features/Tooling/Ideas — OPEN): `ID | Description | Surface | Notes | Server/AAB | Status` (6 columns)
- **Closed tables** (Closed Bugs/Features/Tooling/Architecture): `ID | Description | Surface | Closed | Reason` (5 columns — no separate Status column, since "Closed" + date serves that purpose)
- **"Closed without entry"** (items walked but never added to a real table): `Holding-list # | Item | Status | Reason closed` — a distinct 4-column shape, not one of the four main lists at all

- **Bugs (B)** — broken or incomplete behavior on a user-facing surface
- **Features (F)** — new user-facing capabilities
- **Tooling (T)** — internal dev / test / measurement infrastructure
- **Ideas (I)** — brainstorming-stage entries; deferred-by-design or path-not-chosen items not yet committed as real features

**Numbering** — corrected 2026-07-17 to match actual practice (the original "1=top/2=medium/3=low severity" description never matched how IDs were actually assigned, going back to the earliest entries). The number is a **sequential/session batch counter**, not a severity tier — B9, B10, F17, F19 etc. simply mean "assigned in roughly the Nth batch of items," carrying no priority signal. Letter suffix (`a`, `b`, `c`…) disambiguates within the same batch. **Severity/priority is not encoded in the ID at all** — for a prioritized work order, see the separate priority-queue exercise (ask Claude to regenerate one from current open items; not a static field in this doc).

**Server/AAB** — where the work lands:
- `Server` — Edge Function, SQL, voice server, web; no AAB build required
- `AAB` — mobile code; requires `npx eas build --auto-submit`
- `Both` — server + mobile pieces

**Surface** — which user-facing surface owns the work; used for cross-surface drift discipline (see CLAUDE.md Rule 16). Values:
- `mobile` — work lands on mobile codebase only; no voice change required
- `voice` — work lands on voice-server codebase only; no mobile change required
- `both` — both surfaces; parity required (when one ships, the other must follow before drift)
- `backend` — shared backend (Edge Functions / SQL); both surfaces benefit automatically
- `website` — `mynaavi-website` repo only; neither mobile nor voice
- `staff portal` — staff.mynaavi.com ticket system; not user-facing on mobile/voice/website (added 2026-07-17 — found in use across multiple entries without being a formal enum value)
- `docs` — internal documentation/process artifacts with no runtime surface at all (added 2026-07-17, same reason)

**Architectural principle (Wael 2026-05-08):** every queryable channel = background sync at per-channel depth + live-overlay at question-time. Applies to calendar, email, SMS, WhatsApp.

**Cross-surface drift mechanism:** classification's `Surface` tag is best-effort interim discipline. The mechanical guarantee comes from Voice Completion Roadmap W2 (Anthropic Structured Outputs) + W3 (Voice Automated Regression Suite) — see `docs/VOICE_COMPLETION_ROADMAP_2026-05-08.docx`. Until W2 + W3 land, Surface column + CLAUDE.md Rule 16 (`parity-impact:` on commits) are the human-discipline net.
